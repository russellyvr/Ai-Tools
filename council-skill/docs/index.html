Published for the general public: frontier-grade, dissent-preserving answers at the lowest defensible token cost, with the method's provenance documented on this page.

What it does

Single-model blind spots, corrected structurally.

Invoke as /council (or ask for a multi-model opinion, cross-model consensus, or a deliberated verdict). The skill convenes three heterogeneous frontier models as isolated sub-agents. Each answers the frozen brief independently, then anonymously reviews the other two answers against a fixed rubric. An orchestrating "clerk" — deliberately barred from judging or answering the problem itself — synthesizes a draft and sends it to all three seats in fresh context until every seat returns a valid APPROVE (no FACT, SAFETY or PREFERENCE blocker), or two revision checks are exhausted. The 0-100 agreement score is collected as a diagnostic; it is not the gate. The final report always contains a verdict, the strongest surviving dissent, and a flip condition: the specific evidence that would reverse the verdict.

No model IDs are hard-coded. At every run, Stage 0 fills each seat with its vendor's most capable deep-reasoning model, resolved from the live model catalog. Eligibility is decided by capability, never by product name: distilled and cost tiers (lite, mini, nano, Haiku) and non-chat product lines are never eligible, but a product-name tier such as "Flash" or "Sonnet" is not excluded by its name. When a newer non-flagship generation outranks the newest flagship, the resolver records a tier_conflict and the roster rule decides and discloses the choice. The resolved roster is pinned into the frozen brief, is immutable for the run, and is printed in the final report. If the orchestrator shares a model family with any seat, that same-model conflict is mitigated (anonymization, clerk-only role, peer-only scoring, unanimity gate) but not eliminated — it is disclosed in every final report.

Pipeline

Five stages, hard invariants at each.

  1. Stage 0 — Intake gate. The roster is resolved from the live model catalog (latest deep-reasoning flagship per vendor) and pinned. The user's ask is compiled into a Council Brief (resolved roster, task, ordered criteria, evidence, scope, output form, tool budget) with bracketed defaults for every unclear field. Exactly one pushback is allowed; then the brief freezes. Later ambiguities become named assumptions or flip conditions, never a second interrogation.
  2. Stage 1 — Independent opinions. All three seats launch in one response with an identical prompt and a fixed answer contract (ANSWER / REASONING / ASSUMPTIONS / STRONGEST COUNTERARGUMENT / FLIP CONDITION / CONFIDENCE, ≤1,200 tokens). The roster is never named; peer review is never pre-announced.
  3. Stage 2 — Masked peer review. Each member receives only the other two answers, mechanically scrubbed and fenced as untrusted data, in a deterministically counterbalanced order (every answer is Response 1 for one reviewer and Response 2 for the other). Reviews return anchored absolute rubric scores (accuracy incl. source fidelity, coverage, brief-fit, risk-honesty), errors, ideas worth retaining, self-revisions, an optional ranking with ties allowed, and a ≤300-token STATE_CAPSULE that carries the seat's decision state forward.
  4. Stage 3 — Consolidation. The clerk builds a claim ledger (claim / evidence / support / conflicts) and drafts an attribution-free Draft 0. Evidence dominates: peer rankings inform but never mechanically weight; checkable claims are verified with local tools.
  5. Stage 4 — Consensus loop. Every sourced claim in the draft is first verified against its cited passage. Each seat then judges the draft in fresh context — never shown its own earlier answer or any prior score — on a fixed schema (VERDICT / AGREEMENT_SCORE / BLOCKERS labelled FACT | SAFETY | PREFERENCE / REQUIRED_CHANGES / MAIN_DISSENT / FLIP_CONDITION). Pass = three valid APPROVEs — never averaged, inferred, or overridden; a FACT or SAFETY blocker from any seat is never outvoted. Max two checks; critiques are corrected, rebutted with tool-verified evidence, or preserved as dissent.
  6. Stage 5 — Final report. De-anonymization happens only here. The fixed template emits verdict · answer · why · main dissent · flip condition · assumptions · convergence status with scores · summary table · disclosures, plus an audit manifest.

Design guarantees

Anti-sycophancy and auditability are structural, not aspirational.

  • Clerk, never judge: the orchestrator never scores member answers and never answers the problem itself; peer reviews are the only quality signal.
  • Anti-sycophancy pairing: APPROVE requires BLOCKERS: none; REVISE requires at least one concrete, claim-linked blocker and the change that would clear it — vague vetoes and empty praise are both schema-invalid. Approval means publication approval under the rubric, never established accuracy; a paired-evaluation fixture is required before any accuracy claim.
  • Dissent is never lost: a dropped or outvoted seat's last substantive objection is preserved in the report; a non-unanimous outcome is reported as "not unanimously approved", never papered over.
  • Evidence-gap governance: a seat that believes missing evidence is material returns EVIDENCE_GAP plus a provisional answer; the clerk must either augment the packet and rerun, or print the gap as a named assumption that every seat scores — never silently arbitrate.
  • Token discipline: per-stage output caps, batched launches, blocking reads (never polling), per-seat prompt budgets, and an end-of-run audit manifest recording payload sizes, call counts, scores, and retained dissent.
  • Untrusted-content boundary: everything the orchestrator did not author — evidence packets, file excerpts, fetched pages, peer answers — is relayed only inside UNTRUSTED_DATA fences carrying a standing treat-as-data rule; members run with no shell, file-write, or network tools by default; instruction-shaped constructs are mechanically defanged during the scrub; embedded instructions become findings, never actions.
  • Failure policy: one retry per failed seat, rehydration prompts containing only what a seat was entitled to see, degraded 2-member mode that can never claim formal convergence, and a halt on repeated safety refusals.

Prerequisites

What the skill assumes of the host environment.

  • GitHub Copilot CLI with custom-skill support (skills discovered from ~/.copilot/skills/<name>/SKILL.md) and an active Copilot subscription.
  • A task (sub-agent) tool able to launch background agents with an explicit model and reasoning_effort per dispatch, plus blocking reads (read_agent) and follow-up messaging (write_agent).
  • Deep-reasoning flagship models from Anthropic, Google, and OpenAI in the session's model list. Seats are filled at run time with each vendor's latest flagship, so the skill needs no editing as model catalogs evolve; a vendor with no servable flagship produces a disclosed degraded run, never a substitution.
  • Session-local SQL scratch storage (or equivalent private notes) for the alias↔identity map, which must stay out of member-visible artifacts until Stage 5.
  • Writable run folder at .copilot/council/<run-id>/ for the evidence packet, alias-named artifacts, and the audit manifest.
  • Optional: a Microsoft-verification skill if Microsoft-related claims must be checked during consolidation (the shipped skill references one; remove that line if you don't use it).

Installation

Scripted (recommended) or manual. Installers run as the current user, make no network calls, and never touch your configuration.

# macOS
./install.sh

# Windows (PowerShell 7+)
pwsh -File .\install.ps1          # add -WhatIf to preview

Manual equivalent:

# from this repository root
cp -r skill/council ~/.copilot/skills/council
# restart the Copilot CLI session, then:
/council <your question or decision>

The skill is self-contained: SKILL.md plus three reference files (prompts.md, rubric.md, output-template.md, harness-template.md) loaded progressively per stage. No external services, network calls, or package installs are required beyond the Copilot CLI itself.

Method & cost discipline

How this was built, and what it cost to build it that way.

Multi-model deliberation is expensive by construction — three frontier seats, a cross-review round, and a bounded revision loop. Sustained effort therefore went into making it affordable enough to actually run: per-stage output caps, batched sub-agent launches, explicit prompt budgets, a clerk that orchestrates without ever judging, and an audit manifest that makes every token spent attributable after the fact. The token discipline in SKILL.md is a first-class part of the design, not housekeeping bolted on afterwards.

The specification, rubric, and stage prompts were themselves deliberated across an AI council spanning three independent vendors — each seat answering independently before anonymised cross-review, so that no single model's blind spot could quietly become the spec:

Sources & derivation

Where the method comes from.

  • Andrej Karpathy — llm-council (github.com/karpathy/llm-council): the core method this skill implements — multiple LLMs answer the same query independently, anonymously cross-review each other's answers, and a chairman model synthesizes the final response. The skill adopts the independent-answers → anonymized-review → synthesis pipeline directly.
  • llmcouncil.ai (llmcouncil.ai): the hosted incarnation of the same idea; informed the verdict / main-dissent / flip-condition report framing.
  • Original extensions in this skill (not in the sources): run-time flagship roster resolution (fixed vendors, no hard-coded model IDs); the frozen single-pushback intake brief; the strict all-seats-APPROVE categorical gate with fresh-context, score-blind checks and a bounded two-check revision loop; the clerk-not-judge invariant; STATE_CAPSULE seat-state portability across fresh agents; EVIDENCE_GAP governance; the mandatory untrusted-content boundary (UNTRUSTED_DATA fencing, least-privilege member tool profiles, mechanical defanging of instruction-shaped text); per-stage token/tool budgets; the audit manifest; and the degraded-run and failure-recovery policies. These were developed and hardened iteratively through review rounds run by earlier versions of the council itself.
