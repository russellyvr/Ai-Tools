The problem & the idea

Advisory prose fails; structure doesn't.

Agentic CLIs dispatch a lot of mechanical work — running tests, grepping, collating files, summarizing logs — that a frontier model handles no better than a cheap one, at 10–30× the token cost. Earlier versions of this system tried to fix that with prose instructions ("prefer cheap models for mechanical work"). Measurement showed near-total non-compliance.

Version 3 moved routing out of prose and into structure:

  • Structural pins — settings.json → subagents.agents pins each sub-agent type's default model + reasoning effort (explore/task = ECONOMY low; code-review/research = STANDARD medium). Pins are defaults, not caps: omitting the model parameter applies the pin; setting it explicitly routes up for hard work. Config can't be "forgotten" mid-session.
  • An ambient rubric — a compact 4-row routing table injected into every turn via the CLI's global instructions, with the full specification kept as a reference document.
  • A closed feedback loop — a deterministic analyzer measures actual routing behavior from local session logs; the companion /route-tune skill (published as a separate package) reads the KPIs and applies at most one bounded, logged, reversible change per cycle, then verifies it against the next cycle and auto-reverts on regression.

Core principle: verifiability-first

Cheap routing is lossless only when correctness is checkable.

Tasks are routed by objective features, never intuition:

  • Verifiable — output validated by tests, compiler, linter, schema, or diff. A cheap model + a verification loop equals frontier fidelity by construction.
  • Extractive — the answer already exists in files or output; the model only finds, lists, or summarizes it.
  • Generative + unverifiable — judgment, architecture, ambiguity, security reasoning. Stays FRONTIER, always.

The zero-loss guarantee is an escalation ladder: execute at the routed tier, verify mechanically, and on failure re-run exactly one tier up — never the same tier twice. Worst case costs one cheap attempt extra; the typical case saves the frontier tokens entirely.

The routing table

Deterministic — first match, top to bottom. Tier classes resolve at runtime from the live model list; model names are never hardcoded (hardcoded names went stale in v1).

#Task signatureTierEffort
1Run command/test/build/lint & report; file ops; grep/collate; formatting; log parsingECONOMYlow
2File/symbol search, globbing, "where is X"ECONOMYlow
3Summarize/extract from existing text, logs, diffsECONOMY–STANDARDlow/minimal
4Mechanical single-file edit with machine-verifiable resultSTANDARDlow–medium
5Docs from complete source; pattern-repetitive multi-file change with full test coverage; routine research/reviewSTANDARDmedium
6Debugging, root-cause, non-trivial design; multi-file refactor without full testsFRONTIERhigh
7Security, architecture, ambiguous tradeoffs, irreversible ops, adversarial input, user-facing final synthesisFRONTIERmax (FLOOR)

Tie-breakers: doubt + machine-verifiable → take the lower tier (the ladder protects you); not verifiable → higher tier; hard-to-reverse errors → FRONTIER regardless. A high-stakes override keeps safety/legal/financial/adversarial work high regardless of the row matched. Row 7's max is a floor that never drifts down under cost pressure.

The measurement loop

LLM-free analyzer → KPI targets → bounded tuner → verify & revert.

  1. Measure. analyze_routing.py — a deterministic Python script, no LLM calls — reads the CLI's local session store and per-session event logs and computes four KPIs over a rolling window: frontier cost share; average main-session cache-weighted input tokens per turn (uncached 1.0×, cache-write 1.25×, cache-read 0.1×); ECONOMY share of mechanical dispatches; and sub-agent escalation rate. It appends snapshots to state.json (trend memory), writes report-latest.md, and exits 1 on any KPI breach.
  2. Diagnose. The companion route-tune skill maps each breach to exactly one lever — e.g. escalation rate > 15% ⇒ pins too cheap, raise one class; escalation ≈ 0% for 2+ clean cycles ⇒ try one step cheaper; context bloat ⇒ hygiene advice, not a routing change; frontier share driven by the main session ⇒ advise only (the user's session model is never changed autonomously).
  3. Tune (hard limits). At most ONE pin change and one rubric-wording refinement per cycle; pin moves are exactly one tier class and must stay inside pin_bounds from targets.json; general-purpose and security-review pins, the row-7 floor, and the high-stakes override are untouchable; every change gets an append-only CHANGELOG.md entry with evidence, exact before/after, expected effect, and revert condition.
  4. Verify & revert. Next cycle, the previous change is checked against the KPI it targeted: improved/held → VERIFIED; regressed → exact revert, REVERTED, and a 3-cycle cool-down. Externally-sourced changes (user edits, cross-machine syncs) are logged but exempt from revert logic, so a sync is never blamed for a KPI move it didn't cause.

Design decisions worth stealing

Hardened via cross-machine peer review of a live deployment.

  • Cache-aware cost KPI: raw input-tokens/turn was ~92% cache reads billed at 0.1× — the naive metric overstated context cost by ~5×. Weight tokens by price class before setting targets.
  • Ungameable denominator: "mechanical work" is classified by dispatch surface (the agent_type in the event log), never by intent inferred from prose — so the self-tuner cannot game its own KPI.
  • Quota, not dollars: on subscription billing, savings denominate in premium-request/quota headroom, not currency.
  • Fail open: routing is a cost optimization, not a security gate. Any enforcement hook may deny only unambiguous violations, must log everything, and passes on doubt — a deterministic script cannot grade prompt hardness.
  • Config beats prose (measured): in a 14-day natural experiment on a second deployment, 13 structurally pinned sub-agent definitions produced 834 correctly-routed sidechain messages, while prose-only routing rules produced zero on the same sessions.
  • Pins are defaults, not ceilings: the old "session model is the cost ceiling" rule was deleted — a cheap main session must be free to escalate row-6/7 work up to a frontier model.

Prerequisites

What the deployment assumes.

  • GitHub Copilot CLI with custom-skill support (~/.copilot/skills/), global custom instructions (copilot-instructions.md), and per-sub-agent model/effort pins in settings.json → subagents.agents.
  • Python 3.9+ on PATH for the analyzer (standard library only — no packages to install).
  • The CLI's local session store (session-store.db / per-session events.jsonl logs under ~/.copilot/) — the analyzer's only data source. Nothing leaves the machine.
  • A model list with at least two price classes so ECONOMY/STANDARD/ FRONTIER patterns in targets.json → tier_patterns can resolve; update the patterns when your provider's model names change.
  • Recommended: an OS scheduler (Windows Scheduled Task, cron, or launchd) to refresh the KPI report weekly. The analyzer is the only piece worth automating — it measures, it never tunes. The companion /route-tune skill stays manually run, so a tuning cycle happens only when you invoke it, never on a timer.

Installation

Scripted (recommended) or manual. Installers run as the current user, make no network calls, and deliberately never edit your configuration — behavior-changing steps stay manual and are printed at the end.

# macOS
./install.sh

# Windows (PowerShell 7+)
pwsh -File .\install.ps1          # add -WhatIf to preview

Manual equivalent, plus the configuration steps the installers print:

# from this repository root  (~ = your home directory)
mkdir -p ~/.copilot/routing ~/.copilot/instructions
cp routing/analyze_routing.py routing/targets.json  ~/.copilot/routing/
cp instructions/model-routing.md                    ~/.copilot/instructions/

# 1. Pin your sub-agents in ~/.copilot/settings.json, e.g.:
#    "subagents": { "agents": {
#        "explore":     { "model": "<economy-model>",  "reasoningEffort": "low" },
#        "task":        { "model": "<economy-model>",  "reasoningEffort": "low" },
#        "code-review": { "model": "<standard-model>", "reasoningEffort": "medium" },
#        "research":    { "model": "<standard-model>", "reasoningEffort": "medium" }
#    } }
# 2. Paste the compact routing table (rows 1-7 above) into
#    ~/.copilot/copilot-instructions.md so it is injected every turn.
# 3. Adjust tier_patterns in targets.json to match your live model names.
# 4. Restart the CLI. Optional: install the companion route-tune skill
#    and run /route-tune for the self-tuning loop.

state.json, report-latest.md, and CHANGELOG.md are created by the analyzer/tuner on first run. Re-running the analyzer without new data changes nothing.

Method & cost discipline

How this was built, and why the saving is real rather than rhetorical.

Lowering token consumption is not a side effect of this package — it is the entire point. Routing decisions are made by verifiability, so work whose output can be machine-checked (tests, builds, lint, schemas, exact diffs) or simply extracted from files falls to a cheaper tier losslessly, while generative, unverifiable judgment stays at the top. The pins are structural rather than advisory because an earlier generation proved that prose guidance alone produced measurable non-compliance. The analyzer that scores all of it runs zero LLM calls and reads only local session data, so measuring the saving never costs tokens of its own.

The routing table, tier semantics, KPI definitions and pin bounds were deliberated across an AI council spanning three independent vendors — each answering independently before anonymised cross-review — precisely because a routing rule that is subtly wrong costs more than the tokens it saves:

That cross-vendor pass is also why the KPI denominators are ungameable: a single-model design tends to grade its own homework, and the peer review is what caught it. Claims here are grounded in primary vendor documentation and published prior artifacts rather than model recall — the derivations follow, with original engineering separated from adapted work.

No percentage of savings is claimed anywhere in this package. The mechanisms are documented; the arithmetic is yours to run against your own KPIs, which is exactly what the analyzer is for.

Sources & derivation

Provenance of the design.

  • Original iterative engineering (primary source). The system is v3.1 of a spec developed across three generations on live Copilot CLI deployments: v1 (hardcoded model names — went stale), v2 (advisory prose — measured non-compliance), v3.0 (structural pins + closed tuning loop), v3.1 (cache-aware KPIs and ungameable denominators after a cross-machine peer review between two independent deployments of the same spec).   • GitHub Copilot CLI documentation — the platform surfaces this design depends on: custom skills, global custom instructions, and settings.json sub-agent model/effort configuration (docs.github.com — About GitHub Copilot CLI).
  • Related prior artifacts (independent of this design, cited for context): LLM cascades and cost-aware routing — FrugalGPT (arXiv:2305.05176) and RouteLLM (arXiv:2406.18665). Those route by learned query-difficulty prediction; this system deliberately routes by verifiability and dispatch surface instead, because a deterministic, ungameable classifier was a hard requirement for a self-tuning loop.
